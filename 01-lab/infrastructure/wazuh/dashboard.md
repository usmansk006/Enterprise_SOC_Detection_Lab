# Wazuh Dashboard

## 1. Overview

The Wazuh Dashboard provides the analyst-facing interface for monitoring, investigating, and analyzing security events generated by the Wazuh monitoring infrastructure.

Within this project, the dashboard is used as the primary interface for:

* Security alert monitoring
* Event investigation
* Detection validation
* Threat hunting
* Event correlation
* Host and agent analysis
* MITRE ATT&CK review
* Detection tuning validation

The dashboard converts centralized Wazuh event data into an interface that can be used during day-to-day SOC analysis.

## 3. Primary Analyst Functions

The dashboard supports the following SOC activities:

### Alert Monitoring

Analysts can review generated security alerts and identify events requiring investigation.

### Event Investigation

Individual events can be expanded to inspect structured fields and determine the context surrounding an alert.

### Host Analysis

Analysts can investigate activity associated with specific monitored endpoints.

### Detection Validation

Generated alerts can be compared with the expected behavior of configured detection rules.

### Threat Hunting

Analysts can search available telemetry for suspicious patterns that may not have generated a dedicated alert.

### MITRE ATT&CK Analysis

Where ATT&CK metadata is available, analysts can use technique information to understand the behavioral category represented by a detection.

## 5. Event Investigation

When investigating an alert, analysts should avoid relying solely on the alert title or severity.

Relevant fields should be reviewed where available:

* Timestamp
* Agent name
* Rule ID
* Rule description
* Severity
* Event ID
* User
* Process
* Parent process
* Command line
* File information
* Network information
* MITRE ATT&CK metadata
* Related event fields

The objective is to reconstruct the behavior represented by the alert.

## 6. Filtering and Searching

Common investigation filters include:

```text
Agent
Rule ID
Event ID
User
Process
Command Line
Timestamp
MITRE Technique
Event Source
```

For example, an analyst investigating a specific detection can narrow the dashboard search using the relevant:

```text
Agent → Rule ID → Time Range → Event Details
```

This reduces unrelated telemetry and makes event correlation more efficient.

---

## 7. Time-Based Investigation

Time is a critical investigation dimension.

Analysts should establish:

1. Alert timestamp
2. Events immediately before the alert
3. Events immediately after the alert
4. Related activity within the investigation window
5. Potential process execution sequence

A basic timeline model is:

```text
      BEFORE                 ALERT                 AFTER
───────────────┬────────────────────────┬────────────────────
              │                         │
      Initial Activity          Detection Event       Follow-up
              │                         │
              └────────── Correlation ──┘
```

This helps distinguish isolated activity from a sequence of related actions.

## 14. Evidence Collection

Dashboard screenshots can be useful investigation evidence when they clearly demonstrate:

* Alert details
* Detection rule
* Relevant event fields
* Timeline
* Host information
* ATT&CK mapping
* Correlated activity

Evidence should be captured with enough context to make the finding understandable without exposing unnecessary sensitive information.

Recommended screenshot naming convention:

```text
<PROJECT-ID>-<SOURCE>-<DESCRIPTION>.png
```

Examples:

```text
INV-001-Wazuh-encoded-powershell-alert.png
INV-002-Wazuh-failed-logon-pattern.png
DET-001-Wazuh-event-details.png
```

---

## 15. Evidence Security

Before publishing dashboard screenshots to a public repository, review them for:

* Internal IP addresses
* Hostnames that expose personal infrastructure
* Usernames
* Email addresses
* Authentication information
* API keys
* Tokens
* Session identifiers
* File paths containing sensitive information
* Other personally identifiable information

Sensitive information should be redacted where it is not required to demonstrate the technical finding.

The goal is to preserve the evidentiary value of the screenshot while minimizing unnecessary information disclosure.

## 18. Operational Best Practices

Analysts using the dashboard should:

* Validate alert context before escalating
* Review related events
* Use appropriate time windows
* Correlate multiple telemetry sources
* Avoid treating severity as proof of maliciousness
* Preserve relevant evidence
* Document investigation findings
* Validate detection behavior
* Identify false positives
* Feed tuning requirements back into detection engineering

A dashboard alert is a starting point for analysis, not the final investigation conclusion.
