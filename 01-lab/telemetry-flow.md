# SOC Detection Lab — Telemetry Flow

## 1. Purpose

This document describes the logical flow of Windows security telemetry through the SOC Detection Lab.

The lab uses a Windows 10 virtual machine and an Ubuntu Server virtual machine hosted in VMware. Wazuh provides the endpoint monitoring and detection framework for the project's existing Windows-focused detection use cases.

The documented flow explains the role of each stage without assuming that the complete pipeline is currently operational.

## 3. Stage 1 — Windows Event Generation

Security-relevant activity occurs on the Windows 10 endpoint.

Depending on the configured logging and audit policies, relevant activity may produce records associated with:

- Authentication attempts and failures
- User and account-management operations
- PowerShell execution
- Scheduled-task creation
- Windows Defender detections
- Process creation and parent-child relationships
- CertUtil execution and related file-decoding activity

Not every activity automatically produces a useful event. Event availability depends on the applicable Windows event source, audit policy, logging configuration, and event details.

## 4. Stage 2 — Event Collection

The Wazuh Agent collects configured telemetry from the Windows endpoint and forwards it to the Wazuh server-side environment.

Collection coverage depends on the agent configuration and the event sources enabled for monitoring.

An event being generated by Windows does not necessarily mean it was successfully collected or received by the Wazuh Manager. Those stages must be distinguished when reviewing evidence.

## 5. Stage 3 — Event Processing

The Wazuh Manager processes the telemetry it receives.

Depending on the event type and applicable configuration, processing can include decoding event data, evaluating fields, and applying detection rules.

Detection behavior depends on the event structure, rule conditions, rule dependencies, and the configuration present at the time of processing.

## 6. Stage 4 — Detection Rule Evaluation

The project's existing detection rules target specific Windows security behaviors.

Examples of documented detection categories include:

| Detection category | Relevant telemetry |
|---|---|
| Authentication failures | Windows authentication events |
| Suspicious PowerShell activity | Process or PowerShell-related telemetry |
| Account creation | Windows account-management events |
| Scheduled-task creation | Task-related system events |
| Defender malware detection | Windows Defender event records |
| Suspicious parent-child processes | Process-creation telemetry containing relationship fields |
| CertUtil file-decoding activity | Relevant process-execution telemetry |

The exact event identifiers, field requirements, rule IDs, and rule conditions must be taken from each detection's existing implementation.

These mappings describe the expected relationship between activity and telemetry. They do not independently confirm that every detection has been successfully triggered.

## 7. Stage 5 — Alert Generation

When an event satisfies the conditions of an applicable rule, Wazuh may generate a corresponding alert.

An alert record can help an analyst examine the event, its associated fields, the rule that matched, and the surrounding context available in the monitoring environment.

An alert alone does not establish malicious intent. Analysts should consider the event details, expected system behavior, related activity, and available evidence before reaching a conclusion.

## 8. Stage 6 — Alert Review and Documentation

Where the required services are available, the Wazuh Dashboard can be used to review alerts and investigate event details.

The repository's detection documentation should link each detection to the evidence that supports it, where such evidence exists.

Useful supporting artifacts include:

- Relevant rule or configuration files
- Source event records
- Corresponding alert records
- Historical screenshots
- Existing validation notes
- Documented limitations or dependencies

Evidence should be described according to what it actually demonstrates. A rule file demonstrates the presence of detection logic; an event record demonstrates observed telemetry; a matching alert can support a detection outcome for that recorded event.

## 9. Troubleshooting Boundaries

When a detection does not appear as expected, the telemetry pipeline provides a structured way to understand the possible failure point.

| Stage | Area to investigate |
|---|---|
| Event generation | Was the activity recorded by Windows? |
| Event collection | Was the relevant event source configured for collection? |
| Agent forwarding | Was telemetry forwarded successfully? |
| Event processing | Did the Manager receive and process the event? |
| Rule evaluation | Did the event contain the fields and conditions required by the rule? |
| Alert review | Was an alert generated and is the relevant service available? |

This table describes diagnostic areas; it does not claim that each stage has been tested or that any specific issue has been resolved.
